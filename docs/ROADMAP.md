# Roadmap

Planned work and open ideas, roughly ordered by how soon they're likely to happen. Nothing here is a promise or a deadline — this is a working list for a project developed in spare time by a small team of two.

## Known limitations

Nothing here is an open bug to chase — these are standing constraints of the toolkit, recorded so they are not re-investigated from scratch. (The note-list scroll bugs that once sat here were fixed on 2026-08-30 with a measured root cause; the write-up now lives in `docs/ISSUES_LOG.md`, "The list that lost its place, twice".)

**Theming** — theme switching was ~140ms and visibly flickered; it's now ~26ms and no longer rebuilds anything that didn't change (fixed in 0.32.49). What remains is much smaller and is a plain-Tkinter limitation rather than something this codebase controls: each widget is its own OS window that Windows repaints as soon as its colour is set, so a very brief partial repaint is still possible. See `docs/ISSUES_LOG.md`, "The theme-switch flicker, and three ways not to fix it", before attempting anything further — three approaches were tried and reverted, and the reasons they can't work are recorded there.

## Settings redesign — shipped

Settings is now a list of sections on the left and one open section on the
right, grouped under General / Content / Data / More. The questions this
section used to hold open were answered in the building:

- **Page, not a popup.** Nine settings-related actions open popups of their
  own (the template editor opens nine on its own), and `qa/qa9.py` exists
  because a nested-dropdown-inside-a-popup already broke once. Putting the
  whole of Settings inside a modal would have stacked another layer on that.
- **Flat list, then grouped.** It shipped flat and was grouped shortly
  after: nine entries in one run mixed four different kinds of thing —
  preferences, managers for content you made, tools that delete things, and
  read-only information.
- **The nav does not shrink on a narrow window.** It was built to, and the
  breakpoint could never fire: the app holds its whole content area to at
  least `SIDEBAR_WIDTH + EDITOR_MIN_WIDTH` (900px) and scrolls horizontally
  below that rather than reflowing, so the Settings pane never gets narrow
  enough. The dead code was removed and the reason recorded in
  `settings_page.py`.

The four "still open" quick wins all shipped on 2026-08-30:

- **A "last exported" line in Backup** — shipped: the panel shows the last
  successful export's date and time (failed exports don't move it).
- **Trash retention** — shipped as a real setting: a 7–90 day selector in
  the Trash panel; the purge, the days-left column and every message quote
  it, and unusable hand-edited values read as the 30-day default.
- **A keyboard-shortcut reference** — shipped: Settings → Keyboard
  shortcuts, every bound combo grouped and verified against the bindings.
- **Template deletion** — the confirmation now says plainly it skips the
  Trash and can't be undone. Actually routing templates through the Trash
  (so they'd be restorable like notes) remains a candidate, but it is a
  data-format change, not a quick win.

## Versioning

### Right now: pre-1.0.0

Keep the first number at `0` until the app actually has a real public launch, so `1.0.0` stays meaningful (a clean first release, not used up early).

Until then, the other two numbers are **cumulative all-time totals**, not per-release counts — `MAJOR.<total Added entries ever>.<total Fixed entries ever>`, counted from `CHANGELOG.md`'s `Fixed` and `Added` sections only (across every version section, `[Unreleased]` included). `Changed`, `Testing`, and `Removed` entries don't count — they're neither a shipped fix nor a shipped feature. `docs/ROADMAP.md`'s own "known bugs"/"under consideration" items don't count either, since they're not done yet, and `docs/ISSUES_LOG.md` entries aren't counted separately since they're narrative write-ups of fixes already counted in `CHANGELOG.md` — counting both would double-count the same work.

Bump the version, and cut `CHANGELOG.md`'s `[Unreleased]` section into that new version number (with today's date), every time `note_organizer.py` changes and the app gets rebuilt for real use — the same moment a `.exe` rebuild is already called for. Docs-only changes don't move the version, same as they don't call for a rebuild. If several small PRs land back-to-back before the next rebuild, they share one bump — the trigger is "about to rebuild," not "one bump per PR."

This exists specifically because `APP_VERSION` drives two real things in the code: the backup-before-upgrade safety net in `load_notes()`, and the "Updated to version X" startup banner (`detect_version_change()`) — both only fire when this number actually changes. ### At the real launch: 1.0.0 and after

The version becomes exactly `1.0.0` at the actual public release, regardless of whatever cumulative number it reached beforehand (even `0.150.320` or similar) — the pre-1.0 scheme is explicitly a development-phase convention, not something that carries forward. From `1.0.0` on, standard [Semantic Versioning](https://semver.org/) takes over, and **each number resets to 0 at the release above it** — no more cumulative totals:

- **PATCH** (`1.0.x`) — a release containing only bug fixes, no new features.
- **MINOR** (`1.x.0`) — a release that includes at least one new feature; patch resets to `0`.
- **MAJOR** (`x.0.0`) — reserved for something big enough to warrant it: a real redesign, a breaking data-format change, a genuinely new "generation" of the app. Rare; minor and patch both reset to `0`.

## Under consideration

- **Rich text formatting, continued.** Phase 1 shipped in `0.31.39`: a Bold/Italic/Underline/Strikethrough toolbar and right-click menu, with keyboard shortcuts, applying either to a selection or to whatever's typed next. Phase 2a shipped in `0.32.44`: text color and highlight, added to the same toolbar with swatch-style pickers (no hex-code entry — see `CHANGELOG.md`). Phase 2b shipped in `0.34.51`: paragraph formatting — bullet and numbered lists with multilevel nesting, indentation and alignment (see `CHANGELOG.md` for why numbered levels are not lettered). Quote blocks shipped with it and were removed again in `0.36.54`. Phase 3 shipped in `0.35.51`: font size and family, per selection and as an app-wide default. Phase 4 shipped in `0.37.56`: paste that keeps its source formatting, with Ctrl+Shift+V for plain text, and copy that carries formatting out. **Rich text formatting is complete.** It also turned out to be the foundation tables were waiting on — a pasted table arrives as HTML, `core/richtext.py` is where its `<table>` is understood, and the Tables entry below is what was then built on top of it.
- **Tables — shipped.** `0.39.63` delivered the spreadsheet-style grid (drawn cells, one floating editor, merges, per-column width/alignment/hiding in Markdown's separator-row syntax, block copy/paste round-tripping with Excel, table placement on the page), and the `0.55.81` field-testing marathon grew it up: multi-line cells (`<br>`), per-character styles rendered as runs, a rich live cell editor with an active colour, real checkboxes (`[ ]`/`[x]`), row-height drags, row duplication and auto-scrolling drag-selection. The note's plain text remains the single source of truth throughout — see [ARCHITECTURE.md](ARCHITECTURE.md), "Tables: plain text is the store".
- **Small candidates from the 2026-08-31 idea pass** (put aside deliberately, in rough order of appeal):
  - **The global shortcuts the reference makes you wish existed** — the new Settings → Keyboard shortcuts page shows the gaps plainly: no Ctrl+N (new note), Ctrl+F (jump to search), Ctrl+S (save now). Three bindings plus their reference rows.
  - **Undo on the delete toast** — moving a note to the Trash could offer a one-click Undo right on the confirmation toast, instead of the trip through Settings → Recently deleted.
  - **Import a .md/.html file as a note** — the reverse of the single-note export; `html_to_note` already exists, and a Markdown file's tables/checkboxes are already the note format.
  - **Rebuild only the table block an edit touched** — `_render_table_grids` deliberately tears down and rebuilds every grid in the note ("a grid is cheap to make, and tracking which of them an arbitrary edit invalidated is not"). The 2026-09-02 senior audit measured the cost honestly: ~130ms for a 10-table note per rebuild, run on commits/pastes/menu ops, never on keystrokes — fine today, but it is also the root of the entire view-restore timer complexity (the explicit/ambient contract exists because rebuilt windows map late). Rebuilding only the touched block would cut both the cost and that complexity. An architectural phase with its own design pass, not a patch; measured before, it must be measured after.
- **"Export as PDF" via Edge headless** — phase 2 of the single-note export: `msedge --headless --print-to-pdf` exists on every Windows 10/11, no Python dependency; needs an honest fallback ("saved as HTML, open it and Ctrl+P") for machines where Edge is missing or changes flags.
- **Note list virtualization.** The main note list currently builds a full widget per note on every refresh. Trash and the Share panel already cap what they render up front (see [ARCHITECTURE.md](ARCHITECTURE.md)); doing the same for the main list — or true windowed rendering, building only the cards currently scrolled into view — would help further at very large note counts (many hundreds to thousands).
- **Split the UI into modules.** The data and rules layer is done — thirteen modules under `noteorganizer/core/`, none importing tkinter (see [ARCHITECTURE.md](ARCHITECTURE.md)). **Split the UI into modules — done.** Five areas now live in `noteorganizer/ui/` as mixins: the calculator panel, the Settings page, the dialogs and popups, the calendar, and attachments. All the pure logic went down into `noteorganizer/core/` first. `note_organizer.py` is about 12,700 lines — it dipped when the extractions landed and has grown again through the rich-text, tables and field-testing work, but the pure logic behind all of that went into `core/` rather than into it, which is the point: the entry file is a UI hub, not a junk drawer.

It stopped there deliberately rather than running out of steam. The seams were measured from the call graph (see [ARCHITECTURE.md](ARCHITECTURE.md)) and nothing else clears the bar — the note list keeps 41% of its calls to itself, sharing 33%, open-note tabs 26%, and the editor 17%. The editor barely moved across three extractions, which is the clearest evidence that it is the hub the class turns around rather than a module waiting inside it. What remains in the entry file is genuinely shared surface — the note list, the open-note tabs and the editor all call heavily into each other — and moving any of it into a file would relocate the tangle rather than remove it.

If the UI is ever rebuilt on a different toolkit, that is the moment to revisit this — not before.
- **An Android version.** Nothing decided yet on approach — a full rewrite with a mobile-first toolkit, or a port of the existing logic onto something like Kivy or BeeWare, are both on the table. This is a big enough undertaking that it needs its own scoping pass before any real work starts.
- **Whether to move off plain Tkinter entirely**, decided together with the Android question above rather than separately — the two are linked, since a cross-platform-friendly choice could mean rewriting the UI layer once for both desktop and mobile instead of twice. Candidates worth weighing when that scoping pass happens:
  - **PyQt / PySide (Qt for Python)** — far more capable widgets out of the box (native rich text editing, real tables, more polished look), at the cost of a much steeper learning curve, a heavier package, and (for PyQt specifically) a more restrictive license than this project has used so far.
  - **CustomTkinter** — a modern-looking skin built on top of Tkinter itself, meaning the bulk of the current codebase would still apply; the smallest migration cost of the options here, but also the smallest capability jump.
  - **Kivy** — built with touch/mobile in mind, so it's already on the table for the Android question specifically; would mean rebuilding the desktop UI too if adopted, not just extending it.
  - Doing nothing and staying on plain Tkinter remains a legitimate option — noted here so the decision is made deliberately, not by default.

## Explicitly not planned right now

- Tags as a separate feature from categories — removed in 0.3.0 after concluding categories cover the need on their own; revisiting this isn't currently planned.
- Cloud sync / accounts — the app is intentionally offline-only.
- Recognising tables pasted from a PDF — decided against (2026-08-28). A PDF carries no table structure at all, only text positioned on a page; guessing columns from spacing is a large, unreliable feature of its own. Pasting from a PDF keeps working as it does today — the table's *text* arrives through the normal PDF paragraph-rejoin — and anyone who wants it structured can drop it into a table made from the toolbar. Tables pasted from Excel, Word or web pages (which *do* carry structure) arrive as real grids and stay fully supported.
